  1. Class + date bar. Tapping the chip opens the teacher's own classes (reuses the existing useClassSections pattern) — never a 40-option native <select>. Date defaults to today; no picker unless they explicitly want a past date.
  2. Search. Matches name or admission number, case-insensitive, filters the list live as they type. Client-side — sections top out around 25–40 students.
  3. Filter chips. All / Unmarked / At-risk (<75%), single-select, each with a live count. This is table stakes per rule 1 — not a design idea, an expected control.
  4. Sort. Name (A–Z) default (matches today's API order) · Admission no. · Attendance % (low→high) — the one genuinely "smart" sort, for triage.
  5. Progress card. "Marked X of Y" plus a status breakdown, recomputed on every tap. No spinner, ever — a count.
  6. Row. Avatar initials, name, admission no., attendance % (turns red under 75%). Present/Absent are direct one-tap buttons — never a cycle.
  7. ⋯ overflow. Late, Excused, and a note field live in a small sheet off the row, so the two-button main path never gets cluttered by four statuses.
  8. Mark rest present. The one bulk action. It only touches rows still unmarked — Chetan Shetty (Absent) and Heena Malhotra (Late) are untouched because a human already decided those. 5-second undo toast.
  9. Save. Disabled-looking until everyone has a status; tapping it early opens the same guard sheet as concept 7 (list of who's left, quick P/A buttons) rather than failing silently.

3 · Interaction spec — precise rules

ControlBehaviourEdge case
SearchMatches firstName, lastName or admissionNo, case-insensitive substring, debounced ~150 msNo matches → empty state: "No student matches '…'"
Filter: UnmarkedRows with no status yet this sessionEmpty when everyone's marked — chip shows · 0 and disables itself
Filter: At-riskAttendance % (last 20 school days) < 75 — same threshold as the Attendance ReportCombines with search; does not combine with Unmarked (mutually exclusive)
Sort: Attendance %Ascending — lowest attendance first, ties broken by nameStudents with zero attendance history (new admissions) sort last, not first, with a "no history" tag instead of a false 0%
Present / Absent buttonsDirect set, one tap, no cycling. Tapping the already-active button is a no-opSwitching Present ↔ Absent after Late/Excused was set via ⋯ clears the ⋯ state cleanly
⋯ (Late / Excused)Opens a small sheet: status pills + optional note + time (defaults to now)Closing without picking a status leaves the row exactly as it was — no accidental Present
Mark rest presentBulk-sets only rows with no status. Rows already Present/Absent/Late/Excused are never touchedDisabled (not hidden) when 0 rows are unmarked, so its absence is never a mystery
Undo5-second toast reverts the entire bulk action as one unit, not row by rowA manual tap on any row during the undo window cancels the toast for that row only
SaveEnabled once every row has a status; writes all statuses in one requestTapped early → guard sheet (state 4), never a failed/blocked button with no explanation
2nd-consecutive-absence flagInline banner on the row/guard sheet when a student is absent today and was absent the previous school day — reuses the logic already shown in workflow 1, step 3Only checks the immediately preceding school day, not a rolling window, to keep the rule explainable

4 · API contracts — every one of these already exists and ships today

Finding while speccing this: the existing AttendancePage.jsx calls GET /academic/students to build the roster. That endpoint doesn't return attendance history, so today there is no per-student % anywhere on this screen. GET /academic/attendance/report (already built for the Attendance Report page) returns the roster and the % and the defaulter flag in one response — so this redesign needs one fewer network call than the code it replaces, not one more.
1. Load the roster + attendance % replaces the GET /academic/students call
GET /academic/attendance/report?sectionId={sectionId} // no from/to → server defaults to the last 30 calendar days, same window // the Attendance Report page already shows. Do not compute dates client-side. // 200 response — apps/api/src/routes/academic.js, computeAttendanceStats() { "from": "2026-07-22T00:00:00.000Z", "to": "2026-08-21T00:00:00.000Z", "thresholdPct": 75, // use THIS, never hardcode 75 client-side "classAveragePct": 94, "students": [ { "studentId": "…0402", "firstName": "Kartik", "lastName": "Dutta", "admissionNo": "GPS/2026/0402", "presentCount": 12, "totalCount": 20, "pct": 60, "isDefaulter": true }, … ] }
Use directly, don't recompute: pct drives the row badge and the "Attendance %" sort key. isDefaulter is the "At-risk" filter — it's already computed server-side with the same threshold the Attendance Report uses, so the two screens can never disagree about who's at risk.
2. Load today's marked statuses
GET /academic/attendance?sectionId={sectionId}&date={today} // 200 response — array of AttendanceRecord, subjectId is null for the daily roll [ { "entityId": "…0418", "status": "absent", "subjectId": null, "markedBy": "…" }, { "entityId": "…0411", "status": "late", "subjectId": null, "note": "08:22" } ]
Merge into the roster by studentId === entityId. A student with no matching record is unmarked — never assume present.
3. Second-consecutive-absence check reuses call #2 for one more date
GET /academic/attendance?sectionId={sectionId}&date={previousSchoolDay} // previousSchoolDay = yesterday, rolled back over Sat/Sun (same rule the seed // script uses for schoolDays()). Fire in parallel with call #2, not sequentially.
Flag = today's status is absent and that student's record for previousSchoolDay is also absent. No new endpoint, no new field on AttendanceRecord.
4. Save unchanged from today's code
POST /academic/attendance { "date": "2026-08-21", "sectionId": "…", "subjectId": null, "records": [ { "entityId": "…0418", "status": "absent" }, { "entityId": "…0411", "status": "late", "note": "08:22" } // … one entry per row that has a status ] } // 200 → { "saved": 21 } — validated by markAttendanceSchema, upsert per (tenantId,date,entityId,subjectId)
Upsert means Save is safe to tap more than once — resubmitting the same records overwrites, it never duplicates. Permission: attendance:write, identical to today.

5 · State & logic — what lives in the component, and the four functions that matter

Local state shape
const [searchQuery, setSearchQuery] = useState(''); const [filter, setFilter] = useState('all'); // 'all' | 'unmarked' | 'atRisk' const [sortBy, setSortBy] = useState('name'); // 'name' | 'admissionNo' | 'attendancePct' const [statusMap, setStatusMap] = useState({}); // { [studentId]: { status, note? } } const [guardOpen, setGuardOpen] = useState(false); const [bulkUndo, setBulkUndo] = useState(null); // { studentIds: string[] } | null, cleared after 5s
Persist statusMap to sessionStorage keyed by attendance:{sectionId}:{date}, written on every change. Save is a manual tap in this spec, not autosave — without this, backgrounding the app or an accidental back-swipe mid-roll silently loses everything typed so far. Read it back on mount before falling back to the empty object. This is the one piece of local persistence in scope; it is not an offline write queue.
Derived (memoized, recompute on every dependency change)
const rows = roster.map(s => ({ ...s, current: statusMap[s.studentId] })); const filtered = rows .filter(r => matches(r, searchQuery)) // name or admissionNo, case-insensitive substring .filter(r => filter === 'all' ? true : filter === 'unmarked' ? !r.current : r.isDefaulter); // 'atRisk' — straight from the report response const sorted = [...filtered].sort(bySortBy[sortBy]); // bySortBy.attendancePct: nulls (no history) sort LAST, not first — never read as a false 0% const counts = countBy(rows, r => r.current?.status ?? 'unmarked'); const canSave = rows.length > 0 && rows.every(r => r.current);
Four functions worth writing carefully
function setStatus(studentId, status, extra) { setStatusMap(prev => ({ ...prev, [studentId]: { status, ...extra } })); } function markRestPresent() { const unmarkedIds = rows.filter(r => !r.current).map(r => r.studentId); if (unmarkedIds.length === 0) return; // button stays visible but disabled — never hidden setStatusMap(prev => ({ ...prev, ...Object.fromEntries(unmarkedIds.map(id => [id, { status: 'present' }])), })); setBulkUndo({ studentIds: unmarkedIds }); // toast reads this; auto-clears after 5s } function undoBulk() { if (!bulkUndo) return; setStatusMap(prev => { const next = { ...prev }; bulkUndo.studentIds.forEach(id => delete next[id]); // removes only the bulk-set rows, return next; // a manual edit during the 5s window is untouched }); setBulkUndo(null); } function handleSaveTap() { if (!canSave) { setGuardOpen(true); return; } // never a disabled button with no explanation saveMutation.mutate(buildPayload()); }

7 · Errors, empty states, accessibility

SituationWhat happens
Report call failsRoster still loads from the merge fallback (records only); banner "Attendance % unavailable — retry", the % column and sort-by-% option disable gracefully. Marking is never blocked by this.
Save fails (network/409)statusMap is untouched — nothing clears. Inline error banner + Retry button reuses the same payload.
Empty section (0 students)Reuse EmptyState.jsx: "No active students in this section." No search bar, no Save button.
Search has no matches"No student matches '{query}'" inline in the list area; filter chips and counts stay based on the unfiltered roster, not zero.
Present/Absent buttonsNative <button> pair per row, aria-pressed on the active one — full keyboard operability for free, no custom radiogroup needed.
Bulk undo toastrole="status" aria-live="polite" so a screen reader announces "7 students marked present" without the user needing to find the toast visually.
Guard sheet opensFocus moves to the sheet's first row on open; Esc closes it back to manual marking — it never saves on close.

8 · Testing plan

Unit (Jest) — the four functions in §5 are pure enough to test without rendering: markRestPresent only touches unmarked ids, undoBulk restores exactly those ids and no others, the attendance-% sort puts null-history students last, the second-consecutive-absence check reads two dates correctly across a weekend boundary.

E2E (Playwright) — extend the existing academic/attendance spec: (1) mark a full class via individual taps → Save enabled only at 100%; (2) tap "Mark rest present" with 2 rows pre-set → those 2 stay unchanged, toast shows the other count, Undo restores exactly the bulk-set rows; (3) tap Save early → guard sheet lists the right names → mark all → Save succeeds; (4) filter "At-risk" + sort "Attendance %" → order matches the seeded fixture's known percentages (this repo's Playwright fixtures already seed deterministic data, so exact ordering is assertable).

9 · Definition of done

  • Search filters by name or admission no., debounced, case-insensitive, with a "no matches" state
  • Filter chips — All / Unmarked / At-risk (<75%) — each shows a live count
  • Sort — Name (A–Z) default, Admission no., Attendance % (low→high)
  • Progress card updates on every tap: "Marked X of Y" + P/A/L/E counts + bar, no spinners
  • Present / Absent are one direct tap each — no cycling through four states
  • Late and Excused live behind ⋯ and never appear as default buttons on the row
  • Mark rest present only affects rows with no status yet; 5-second undo for the whole action
  • Save is guarded, not blocked — early save opens the "who's left" sheet, never fails silently
  • 2nd-consecutive-absence banner appears using the same rule as the workflow storyboard
  • Zero new API endpoints; filter/sort/search are client-side only — roster + % load from GET /academic/attendance/report (§4.1), not GET /academic/students
  • statusMap persists to sessionStorage per section/date so backgrounding the tab mid-roll doesn't lose progress (§5)
  • 7 new components under components/attendance/ match the contracts in §6; AttendancePage.jsx is rewritten, not replaced
  • Error, empty and no-match states match §7; Present/Absent buttons are keyboard-operable with aria-pressed
  • Unit tests cover the four functions in §5; Playwright covers the four scenarios in §8
  • Verified against the real Grade 5-A / Friday 21 Aug scenario used throughout this spec
