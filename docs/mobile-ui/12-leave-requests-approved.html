  1. One request, full context — reason and remaining balance visible without a click-through.
  2. Progress bar. "1 of 36" makes the size of the queue honest instead of an endless table.
  3. Approve/Reject advance to the next card automatically — no re-navigating to the list.
Why Mock 2 is approved: 36 pending requests is exactly the size where a table forces re-scanning after every action. The queue pattern mirrors the already-approved Attendance Report follow-up queue (concept 4) — same shape, different domain: one item, full context, act, advance.

2 · API contracts — every one of these already exists

GET /staff/leave-requests?status=pending&page=1 // unchanged — client renders one request at a time from the array instead of a table PATCH /staff/leave-requests/{{id}}/approve PATCH /staff/leave-requests/{{id}}/reject {{ "comment" }} // unchanged — both advance the queue to the next card on success
"Balance after" needs one extra fetch per card: GET /staff/leave-balances?staffId={{id}}, already used elsewhere (LeaveRequestsPage.jsx's own balance strip for "my requests"). Fire it lazily for the card in view, not all 36 up front.
