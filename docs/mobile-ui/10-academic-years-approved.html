  1. Active year card. Its terms are always expanded — no reason to hide the context every other screen is currently using.
  2. "current" tag. The one term whose date range contains today. Pure date-range math, no new field.
  3. Collapsed terms. Inactive years show a count; tapping expands in place — no navigation away from the list.
  4. ＋ Add a term. Opens a 3-field sheet (Name, Start, End) and calls the POST /academic/terms endpoint that already exists and has never had a UI.
  5. Set active. One tap, one confirm — this changes what every other screen defaults to, so a bare tap with no confirmation would be too easy to trigger by accident.
  6. ＋ New year. Unchanged from today, except the confirm now says what actually happens: the new year becomes active immediately.
Why Mock 2 is the approved one, not Mock 1: Mock 1 is a legitimate, shippable screen — it's exactly what exists today, just mobile-shaped. But three other approved/planned screens (Grades, Grade Report, Report Cards) already depend on terms existing, and right now nobody can see or create one without the API directly. Mock 2 costs two small additions and closes that gap for good. It does not add filter, search or sort — with 3 years and 6 terms, none of those would do anything useful, which is exactly the point of rule 1: add only what the data actually needs.

2 · API contracts — every one of these already exists

1. Load years and their terms 2 calls, both existing
GET /academic/years // 200 — sorted startDate desc, cached 300s server-side (withCache) [ { "_id": "…128", "name": "2026-27", "startDate": "2026-04-01…", "endDate": "2027-03-31…", "isActive": true }, { "_id": "…", "name": "2025-26", …, "isActive": false }, { "_id": "…", "name": "2024-25", …, "isActive": false } ] GET /academic/terms?yearId={yearId} // 200 — sorted startDate asc. Fire once per expanded year, not all 3 up front. [ { "_id": "…", "name": "Term 1", "startDate": "2026-04-01…", "endDate": "2026-09-30…" }, { "_id": "…", "name": "Term 2", "startDate": "2026-10-01…", "endDate": "2027-03-31…" } ]
"current" is computed client-side: the term where startDate ≤ today ≤ endDate. No new field, no new endpoint — the year list already tells you which one is active, and the date range tells you which term is current.
2. Create a term endpoint exists, never called from the UI until now
POST /academic/terms { "academicYearId": "…", "name": "Term 1", "startDate": "2027-04-01", "endDate": "2027-09-30" } // 201 → the created term. Permission: tenant:admin. No overlap validation server-side — // the form should warn (not block) if the new range overlaps an existing term.
3. Create / activate a year unchanged from today's code
POST /academic/years { "name", "startDate", "endDate" } // 201 — server deactivates every other year for this tenant FIRST, then creates this // one as active. The confirm dialog before this call must say so explicitly. PATCH /academic/years/{id}/activate // 200 — same deactivate-then-activate; invalidates the 300s years cache server-side
Both writes are tenant-admin only. A user with only students:read (most staff) sees this whole screen read-only — the ＋ New year button, Set active chip, and ＋ Add a term all need to check permissions.includes('tenant:admin') and simply not render if absent, exactly like TimetablePage.jsx already does for its admin-only actions.

6 · Definition of done

  • Active year's terms are expanded by default; inactive years collapse to a count
  • The term containing today's date is tagged "current" — computed client-side, no new field
  • ＋ Add a term calls the existing POST /academic/terms; warns (doesn't block) on date overlap
  • Set active always confirms first and its copy explains the app-wide effect
  • ＋ New year's confirm explicitly states the new year becomes active immediately
  • All four write controls are hidden (not disabled) for users without tenant:admin
  • No filter, search, or sort control was added — the dataset doesn't need one, and adding one would fail rule 1
  • Verified against the real seeded years/terms (2024-25, 2025-26, 2026-27 active, today inside 2026-27 Term 1)
