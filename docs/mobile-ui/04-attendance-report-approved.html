Share summary card
  1. Ring + defaulter count. The number people actually came for, above the fold.
  2. Default sort: worst first. Not alphabetical — the whole point of the screen is triage.
  3. Share, not export. Renders the same summary as an image/PDF for WhatsApp instead of a CSV nobody opens on a phone (same pattern as Attendance concept 4's share card, already approved there).
Why Mock 2 is approved: "who needs a call today" is this screen's entire job, and Mock 1's alphabetical-by-default table buries that under a scroll. Sort-worst-first and a share card cost nothing new on the backend — computeAttendanceStats already returns isDefaulter and pct per student; the change is presentation order and an export format, not new data.

2 · API contracts — every one of these already exists

Same single endpoint, sorted client-side
GET /academic/attendance/report?sectionId={id}&subjectId={optional}&from={d}&to={d} // 200 — unchanged from today. Client sorts students[] by pct ascending instead of // the server's default (lastName, firstName) order — zero backend change. { "classAveragePct":94, "thresholdPct":75, "students":[{{ "studentId","firstName","lastName","admissionNo","presentCount","totalCount","pct","isDefaulter" }}] }}
Guardian phone for the Call chip comes from Student.parentContacts[0].phone — already on the student document, just not currently joined into this report's response. One field to add server-side: parentContacts in the Student.find() projection.
